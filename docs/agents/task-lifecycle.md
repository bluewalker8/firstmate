# Task lifecycle

Load when: classifying, briefing, spawning, promoting, delivering, or completing a ship or scout task.

Fresh sources: `bin/fm-brief.sh`, `bin/fm-spawn.sh`, `bin/fm-promote.sh`, `bin/fm-review-diff.sh`, `bin/fm-pr-check.sh`, and their current `--help`, headers, and output.

## Intake and brief

A ship delivers a project change.
A scout delivers knowledge in a report and never opens a PR.
An implementation request includes shipping even if diagnosis is required first.
A diagnosis or assessment request stops at evidence-backed findings unless the active instruction also authorizes a change.

Create the standard brief with `bin/fm-brief.sh` and inspect its current `--help` before choosing task-specific flags.
Replace every remaining task placeholder with a bounded objective, acceptance criteria, relevant context, project-specific verification, and active prohibitions.
Do not copy the root constitution or unrelated references into the brief.

The brief must make the assigned identity explicit.
A ship or scout is an autonomous worker, not a primary Firstmate.
Its repository path does not change that identity.
The worker executes the brief directly and does not run Firstmate session startup or recursively delegate.

No brief may delegate a PR merge, forced teardown, production mutation, destructive or irreversible action, security-sensitive decision, or client-money-touching decision without exact active authorization.

## Spawn and status

Inspect `bin/fm-spawn.sh` `--help` and its header immediately before dispatch.
Use only a verified harness and the active dispatch profile selected from current configuration.
The spawn must resolve to an isolated task worktree distinct from the primary project clone.
Treat any isolation refusal as a blocker rather than bypassing it.

Workers report only supervisor-actionable phase changes and terminal states.
Long context for a decision belongs in the task discussion file named by the generated brief.
Use short steering messages and place detailed corrections in a file the worker can read.

## Ship delivery

The active brief defines validation mode and project-specific commands.
The worker reviews its complete change against the authoritative base, runs relevant checks, records failures faithfully, pushes the feature branch when required, and opens a PR through the configured GitHub tool.
Firstmate records and watches the PR through `bin/fm-pr-check.sh` after the worker reports the full URL.
Ready means ready to request merge authorization.
It does not authorize a merge.

For local-only delivery, the worker stops on its feature branch.
Primary Firstmate reviews through `bin/fm-review-diff.sh` and uses the guarded local merge helper only after current captain approval.

## Scout delivery and promotion

A scout may make disposable local changes and scratch commits for investigation.
It never pushes and never opens a PR.
Its durable deliverable is the report path generated by its brief.
Read and relay the report before teardown.

If the captain asks to ship a scout finding, inspect `bin/fm-promote.sh` before promotion.
Promotion restores ship teardown protection.
The ship branch begins from a clean authoritative base and carries only intended changes.
The reproduction becomes a regression test when applicable.

## Completion

Do not mark work complete from intention, an old status event, or an idle endpoint.
Observe the report, branch, PR, checks, merge, or delivered state required by the active brief.
After safe teardown, update the active backlog through the mechanism in the state reference.
